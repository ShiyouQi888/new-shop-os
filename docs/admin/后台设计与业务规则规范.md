# 后台设计与业务规则规范

版本：1.0<br>
适用范围：Shop-OS 管理后台、商城订单与代理权益服务<br>
目的：让后台界面、权限、订单状态、资金口径和履约操作使用同一套规则，避免页面显示与服务端账务各说各话。

## 1. 设计原则

后台的首要任务是安全、准确地完成运营动作。界面先呈现对象身份、当前状态、金额口径和下一步可执行操作，再呈现辅助信息。关键动作必须让操作者知道影响对象、金额、状态变化和不可逆后果。

### 1.1 视觉与布局

| 类别 | 规范 |
|---|---|
| 品牌主色 | `#FF6B35`，用于主要操作和当前选中态 |
| 主色交互 | Hover `#E85222`，按下 `#D9471A` |
| 成功 / 警告 / 危险 | `#18A66A` / `#F5A623` / `#E5484D` |
| 文字 | 主文字 `#171A1F`，正文 `#626A73`，弱文字 `#9AA1AA` |
| 页面与卡片 | 页面 `#F8F9FB`，卡片 `#FFFFFF` |
| 边框 | `#E7E9ED`；状态不能只靠颜色表达，必须同时有文字 |
| 间距 | 以 4/8/12/16/20/24/32 px 为节奏，页面区域按 8 px 网格对齐 |
| 圆角 | 控件 6–8 px，数据卡片 12 px；同类组件保持一致 |
| 页面结构 | 标题与说明 → 页面级操作 → 筛选区 → 数据表/内容区 → 分页或汇总 |
| 内容密度 | 表头 46 px、数据行约 50 px；数字和金额右对齐、使用等宽数字 |

品牌橙只强调可操作重点，不用于大面积底色。危险动作使用危险色，并通过二次确认说明后果；“通过退款”“打款”“删除商品”等动作必须能追溯操作人和业务单号。

### 1.2 页面与组件状态

每个数据页面必须支持：首次加载、刷新加载、空结果、请求失败、无权限、部分数据缺失。表单需要明确必填项、单位、输入范围、保存状态和服务端错误。列表筛选和分页应保留当前条件；详情页应展示状态时间线和来源单据。

交互约定：

- 查询、刷新、保存、批量操作分别提供独立 loading 状态，避免重复提交。
- 批量操作先说明数量和统一使用的数据，再执行；服务端限制批量上限并逐条报告成功/失败结果。
- 禁用状态必须说明原因；危险操作不得只靠按钮变灰。
- 表格操作列固定在右侧时，不遮盖主要数据；小屏使用横向滚动或详情抽屉。
- 图表注明统计口径、时间范围、时区和退款处理规则，不能把“订单数”误标成“付款数”。

## 2. 权限与职责

权限由服务端按每次请求实时查询角色权限，不以菜单隐藏代替接口授权。新增页面时必须同时定义菜单权限与 API 权限；敏感配置和资金动作采用最小权限。

| 角色 | 主要职责 | 禁止默认授予 |
|---|---|---|
| 超级管理员 | 全系统配置、管理员和角色管理、审计 | 不适用于日常共用账号 |
| 运营 | 商品、订单履约、会员、权益、工单、转卖运营 | 支付密钥、管理员/角色管理、财务总览 |
| 财务 | 资金总览、佣金规则、提现审核/打款、佣金和领货查询 | 商品成本批量导出、系统支付密钥、管理员管理 |
| 客服 | 订单查询与限定售后、会员查询、工单处理 | 退款以外的资金操作、商品/权益规则配置 |

本次补齐的服务端边界包括：订单和商品查询要求对应查看权限；佣金、领货、转卖、财务页面要求业务权限；支付和基础站点配置要求 `system:admin`；权益和分销配置按配置分组授权。UI 菜单只作为入口控制，API 仍必须独立拒绝越权请求。

## 3. 金额与数据权威来源

### 3.1 商品 SKU 价格字段

| 字段 | 用途 | 能否参与订单/佣金/退款 |
|---|---|---|
| `price` | SKU 销售价；会员折扣的计算基价 | 是 |
| `market_price` | 前台营销参考价/划线价 | 否 |
| `cost_price` | 后台内部采购或成本参考 | 否；只用于内部毛利分析 |
| `order_item.unit_price` | 下单时服务端计算并固化的成交单价 | 是，作为订单历史快照 |
| `order_item.original_price` | 下单时 SKU 销售价快照，不是营销参考价 | 仅用于订单历史展示 |

会员折扣按 `price × shop_discount / 100` 计算，商品配置为排除折扣时使用 `price`。营销参考价只可用于对比展示。新订单的金额必须来自服务端，不接受前端提交的单价或总价。

旧数据库中含义不清的 `product_sku.original_price` 会迁入 `market_price`；旧 `cost_price` 置为 0，须由管理员核实后重新录入，不能把旧值自动认作真实成本。订单明细仍保留历史 `original_price` 快照。

### 3.2 订单金额

普通商品：

```text
商品原销售额 = Σ(SKU.price × 数量)
商品成交额 = Σ(适用会员折扣后的 SKU 成交单价 × 数量)
优惠金额 = max(商品原销售额 − 商品成交额, 0)
运费 = 服务端运费规则计算结果
应付金额 = 商品成交额 + 运费
```

目前普通商品运费规则由后台系统配置 `shipping.default_fee` 与 `shipping.free_threshold` 控制；满额判断使用折扣后的商品成交额。礼包按礼包售价结算，礼包内 SKU 仅用于履约快照。前端可展示运费预估，但订单、支付单和退款必须使用服务端最终金额。

所有金额写入前按两位小数规整。不能用二进制浮点累计值作为最终财务值；未来接真实支付前，应将账务金额迁移到整数分或定点数存储。

## 4. 订单、支付与售后规则

### 4.1 订单状态

| 状态 | 名称 | 可进入状态 |
|---:|---|---|
| 0 | 待支付 | 1 已支付待发货、4 已取消 |
| 1 | 待发货 | 2 已发货、5 退款中 |
| 2 | 待收货 | 3 已完成 |
| 3 | 已完成 | 退款需走售后流程，不可直接改状态 |
| 4 | 已取消 | 终态；待支付订单释放库存 |
| 5 | 退款中 | 1 驳回后恢复待发货、6 退款完成 |
| 6 | 已退款 | 终态 |

状态变更必须使用当前状态条件更新（compare-and-set），并与库存、钱包、额度、佣金和审计流水放在同一数据库事务中。不能允许后台把已付款订单直接改成“已取消”来绕过退款。

### 4.2 支付

支付单金额必须等于订单服务端 `pay_amount`；同一待支付订单重复请求应复用未完成支付单。支付成功只将实物订单置为待发货，不能把“支付成功”伪装成“履约完成”。礼包会员权益在支付成功后激活，礼包实物仍需发货。

当前实现：模拟支付可完整驱动订单、礼包激活、消费返还额度和账务流水；微信/支付宝只有配置入口和 Provider 抽象，尚未实现真实下单签名、验签回调、退款、关单、账单下载和渠道对账。服务端禁止将 `payment.mode` 切换到 `real`，此限制必须保留到真实闭环完成。

### 4.3 退款

当前只开放已支付、未发货、普通零售订单的整单退款申请。退款处理中保留库存占用；审核通过时模拟退款记录支出、恢复库存并回滚关联佣金；驳回必须填写原因并恢复为待发货。礼包、领货权益订单和已发货订单不能走这条简化路径，需等待权益冲回、退货收货、部分退款和真实渠道退款实现。

## 5. 库存、领货、转卖和钱包

### 5.1 库存

下单时在同一事务内按 `stock >= quantity` 扣库存并记录订单明细；支付前取消、审核通过退款时恢复库存。扣减、恢复和订单状态必须同事务、具备幂等性，禁止库存变负。礼包明细也必须逐 SKU 扣减并校验上下架。

### 5.2 月度领货额度

领货额度不是钱包余额，不可直接按现金提现。每次发放、兑换、后台调整、转卖扣减和回补都必须产生 `credit_flow`，余额需与流水核对。调整额度不能扣穿已使用金额，扣减不得大于剩余额度；待支付的现金差额订单先预留额度，支付成功后才正式扣减，取消时释放预留。

`resellable_amount` 表示额度中可以转卖的部分，且必须满足 `0 ≤ resellable_amount ≤ remain_amount`。兑换先消耗不可转卖额度，只有余额低于可转卖额度时才减少可转卖部分。

### 5.3 转卖

转卖金额由服务端根据可转卖额度、当前服务费率和运费生成不可变单据快照：

```text
服务费 = round(金额 × 服务费率, 2)
预计结算 = 金额 − 服务费 − 快递费
```

权益在申请时冻结/扣出，待匹配或匹配中可以取消并恢复额度及可转卖额度；匹配完成后进入待结算，不再提供取消入口。相同零售/礼包订单不能被多个有效转卖单重复匹配；匹配订单必须确实包含当前转卖商品池中的 SKU。完成结算时应校验金额快照，将结算款入会员钱包、记录平台流水和管理员审计。

当前匹配表达的是“真实订单需求信号”，不是对实际零售订单的履约转单。转卖结算目前只记内部钱包和模拟流水，未接银行/支付渠道出款、物流承运商订单和外部对账。

### 5.4 钱包与提现

钱包余额、冻结金额、累计收入和累计提现必须互相一致。申请提现时从可用余额转入冻结；审核驳回时原额解冻；审核通过转为待打款；确认打款时释放冻结并记录渠道交易号。任何步骤发现冻结金额不足时必须整笔回滚并提示人工核对，不能按可用部分“凑数”。手续费与实际到账额按两位小数计算。

当前后台“打款完成”表示运营人员登记已完成，并非系统调用银行/支付宝实际打款。生产环境必须接出款 Provider、幂等键、失败重试、回单或交易查询、日终对账后，才可视为真实出款闭环。

## 6. 三级分销与佣金

推荐关系应在注册时固化为直属、二级、三级关系；每个用户在自己的关系树中只能出现一次，不能出现自邀或环路。佣金只从符合规则的礼包订单按实际应付金额计算，最多三级，按等级和层级配置费率；关闭总开关或对应层级时不产生该层佣金。

佣金状态：0 待结算，1 已结算至钱包可提现，2 已随提现标记为已提现，3 冻结，4 回滚。佣金结算周期从订单确认收货/完成开始，按 `commission.settle_days` 到期后转入钱包；财务查看佣金列表时会触发已到期佣金结算。结算操作必须以佣金仍为待结算为条件，状态更新、钱包入账、财务流水必须同一事务。

已发佣金发生退款时，如果钱包余额不足以全额追回，当前记录只会追回可用余额并在回滚原因中记下欠款；尚无独立应收债权、追缴流程和清偿流水。这是上线前需补齐的风险控制项。

## 7. 财务口径与审计

### 7.1 大盘口径

财务大盘的累计收款包含已经完成退款的订单原始支付额，另列已退款金额；退款中订单仍视为已收款，同时计入待退款风险敞口。收支净额估算按“累计订单收款 − 已退款 − 已打款提现”计算。转卖完成只把站内额度转为钱包余额，在实际提现之前不是外部现金流出，不能与后续提现重复扣减。页面还分别展示钱包余额/冻结、待结算佣金、待转卖结算、可转卖额度估算和待履约金额。

资金覆盖率只针对当前系统已建模的现金负债进行估算。领货可转卖额度按每笔额度分别扣服务费和快递费估算；仅可领取额度单独列为履约风险，不与现金风险混加。页面必须明确：当前估算不是银行余额、会计利润或完整资产负债表。

### 7.2 流水和审计

每次付款、退款、佣金结算/回滚、转卖服务费与结算、提现冻结/解冻/打款、领货额度增减，都应能追到业务单号、操作时间、操作人、前后状态和金额。`credit_flow`、订单状态审计、管理员操作日志和 `finance_flow` 的用途不同，不能互相代替。

当前 `finance_flow` 是简单的正负金额流水，不是复式总账；其余额是应用内顺序累计值，没有期初银行余额、科目、借贷方向、外部交易号唯一约束或银行对账。页面将它作为内部业务流水展示，不可宣称为已对账资金余额。

## 8. 后台模块验收约束

| 模块 | 必须满足的业务验收 |
|---|---|
| 商品与 SKU | 销售价、营销参考价、内部成本分别维护；库存变更可追踪；上下架不删除历史订单快照 |
| 订单 | 从服务端计算商品、折扣、运费、应付；订单详情展示 SKU、数量、支付、物流和售后时间线 |
| 售后 | 仅合法状态可申请/审核；权限分离；退款金额、渠道结果和库存恢复可追踪 |
| 分销 | 关系链可解释；佣金展示基数、费率、层级、结算时间；撤销和追缴必须有负债处理 |
| 提现 | 可用/冻结/已提现金额分开；审核与打款是两个状态；实际到账金额和交易号可查 |
| 转卖 | 费用快照明确；匹配来源可查；权益回补与钱包入账不可重复；已匹配订单不可撤销 |
| 文件与配置 | 文件管理和配置按职责授权；支付凭证仅系统管理员可读；密钥不应进入普通日志 |
| 仪表盘 | 所有指标有口径、时间范围和权限；待办数量对应可访问页面；异常和加载失败有反馈 |

## 9. 当前已落地与上线前缺口

### 已落地

- 后台统一暖橙色设计变量、页面容器、卡片、筛选、表格、焦点样式和数据密度。
- 经营工作台呈现今日实收、待处理事项、经营指标和趋势，服务端按支付时间统计收款。
- 订单、商品、佣金、领货、转卖、财务和敏感配置接口补充服务端权限。
- SKU 销售价/营销参考价/内部成本拆分；营销参考价不进入资金计算。
- 订单库存扣减、支付、退款、钱包、转卖和领货关键写入采用事务或状态条件更新。
- 运费规则由服务端配置和计算，前台运费仅为预估；订单响应返回服务端金额快照。
- 转卖取消恢复可转卖额度；匹配限制真实需求商品；匹配与结算写管理员审计。
- 财务大盘避免把累计净收支估算称为实际银行余额或利润。

### 真实经营前仍需补齐

1. 微信/支付宝真实支付创建、签名、回调验签、幂等、关单、退款和对账。
2. 提现渠道自动出款或可靠人工回单流程，失败重试和银行流水核对。
3. 已发佣金回滚不足时的应收债权、冻结、追缴和清偿机制。
4. 已发货退货、部分退款、运费/优惠券分摊、退款原路退回和库存质检回库。
5. 转卖匹配与真实履约、物流承运、运费支出和转卖款外部资金来源的闭环。
6. 复式会计账、期初资金、采购/商品成本、支付渠道手续费、税费、物流成本、银行对账和关账流程。
7. 支付密钥加密存储、轮换、权限脱敏、密钥操作审计；生产环境密钥应迁移到安全密钥管理服务。
8. 过期领货额度的定时作业、到期通知、转卖申请中的额度处理与争议售后规则。

在这些能力完成前，系统应保持模拟支付和模拟出款语义，不得把内部状态变更作为真实资金到账的证明。
